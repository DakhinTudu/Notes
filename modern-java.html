1. Modern Java: The Evolution of Writing Code

Imagine you are writing a letter.

  • Old Java (Pre-8): You have to describe every single hand movement: pick up pen, touch paper, move right, lift pen. (Imperative).
  • Modern Java (8+): You just say "Write 'Hello'". You focus on the intent, not the mechanical execution. (Declarative).

The Main Shift

Modern Java is about moving from How to What. Instead of writing 10 lines of code to loop through a list and find a user, you write 1 line that says "Give me the user where name is Daxin".

Real World Example: Finding an Item

// OLD WAY (Imperative)
User found = null;
for (User u : users) {
    if (u.getName().equals("Daxin")) {
        found = u;
        break;
    }
}

// MODERN WAY (Declarative)
User found = users.stream()
    .filter(u -> u.getName().equals("Daxin"))
    .findFirst()
    .orElse(null);

2. Functional Interfaces: The "Grammar"

Before you can use Lambdas, you need to understand the "Container" they fit into. That container is a Functional Interface.

What is it exactly?

It's just an interface with only one abstract method. If it has more than one, it is NOT functional. Java uses the @FunctionalInterface annotation to help the compiler enforce this.

The 4 Universal Patterns

Java provides 4 standard interfaces that cover almost every scenario. Learn these and you won't need to define your own.

graph TD A[Data In] --> B{Process Type} B -->|Return Boolean| C[Predicate] B -->|Transform Data| D[Function] B -->|Consume Only| E[Consumer] B -->|Generate Only| F[Supplier]
  1. Predicate<T>: Takes one input, returns true/false. 
    Predicate<Integer> isOldEnough = (age) -> age >= 18;
  2. Function<T, R>: Takes input T, returns result R. 
    Function<String, Integer> strLen = (s) -> s.length();
  3. Consumer<T>: Takes input, returns nothing (void). 
    Consumer<String> logger = (msg) -> System.out.println(msg);
  4. Supplier<T>: Takes nothing, returns a value. 
    Supplier<Double> random = () -> Math.random();

The Default Method "Diamond Problem"

Modern interfaces can have default methods. If you implement two interfaces that have the same method name, you get a Diamond Problem.

interface A { default void hello() { out.print("A"); } }
interface B { default void hello() { out.print("B"); } }

class MyClass implements A, B {
    @Override
    public void hello() {
        A.super.hello(); // You MUST explicitly choose which one to call
    }
}

3. Lambda Expression Deep Dive

A Lambda is essentially a method without a name that you can pass around as data.

Evolution: From Anonymous to Lambda

Level 0: Java 7 (Anonymous Class)

Runnable r = new Runnable() {
    @Override
    public void run() {
        System.out.println("Hello");
    }
};

Too much "boilerplate" (useless code).

Level 1: Basic Lambda

Runnable r = () -> {
    System.out.println("Hello");
};

Level 2: One-Liner Perfection

Runnable r = () -> System.out.println("Hello");

Under the Hood (For Advanced Learners)

Is a Lambda just a shortcut for an Anonymous class? NO.

  • Memory: Anonymous classes create a new .class file for Every. Single. Instance. (Heavy).
  • Mechanism: Lambdas use a JVM instruction called invokedynamic. They are executed as private methods on the class they are defined in. They are much faster and lighter.

4. Method References: The Final Stage of Clarity

If your Lambda just calls a method that already exists, don't write the lambda. Use a Method Reference (::).

Pattern Lambda Method Reference
Static Method (s) -> Integer.parseInt(s) Integer::parseInt
Instance Method (s) -> System.out.println(s) System.out::println
Constructor () -> new ArrayList<>() ArrayList::new

Code Example: Cleaning a String List

List<String> names = List.of(" daxin ", " tudu ", " java ");

// Lambda Way:
names.stream().map(s -> s.trim()).forEach(s -> System.out.println(s));

// Method Reference Way (Cleaner):
names.stream().map(String::trim).forEach(System.out::println);

5. Stream API: The Data Pipeline

A Stream is a sequence of objects that you can process in a pipeline. Important: A Stream does NOT store data. It only moves data from a Source (like a List) to a Destination.

graph LR S[Source: List/Set] --> I1[Intermediate: filter] I1 --> I2[Intermediate: map] I2 --> T[Terminal: collect] T --> R[Result: New List/Map]

Why use Streams?

Because they are Lazy. If you have a list of a million items and you only need the first 3 that pass a filter, Java will stop looking at the list as soon as it finds those 3. A traditional for-loop wouldn't be this smart automatically.

The Basic Pattern

List<String> result = list.stream()   // 1. Create Stream
    .filter(s -> s.length() > 5)     // 2. Intermediate Op
    .limit(3)                        // 3. Intermediate Op
    .toList();                       // 4. Terminal Op

6. Intermediate Operations: Transforming Data

These methods return a new Stream. They are lazy—they don't execute until you call a terminal method.

  • filter(Predicate): Removes unwanted items. 
    .filter(name -> name.startsWith("D"))
  • map(Function): Changes the type or content. 
    .map(User::getEmail) // Converts User object to String email
  • flatMap(Function -> Stream): Used for nested collections. "Flattens" multiple streams into one. 
    // List of Orders -> Each has List of Items -> flatMap gives 1 Stream of Items
.flatMap(order -> order.getItems().stream())
  • distinct(): Removes duplicates based on equals().
  • sorted(): Sorts the stream.
  • peek(Consumer): Used for debugging. Doesn't change data. 
    .peek(u -> System.out.println("Processing: " + u))

The flatMap Visual Trace

Think of flatMap as an "Unwrapper".

// 1. You have a list of Lists: [[A, B], [C, D]]
// 2. Map would give you: Stream of [A, B] and Stream of [C, D] (Nested!)
// 3. FlatMap "flattens" the folders:
//    [A, B, C, D]

7. Terminal Operations: The End of the Road

These methods trigger the execution of the pipeline and return a final value (not a stream).

  • forEach(Consumer): Do something with every item (e.g., Print).
  • collect(Collector): Convert back to a List, Set, or Map.
  • count(): Returns the number of items.
  • anyMatch / allMatch / noneMatch: Returns boolean. Perfect for validation.
  • findFirst / findAny: Returns an Optional.
  • reduce(Identity, accumulator): Combines all items into one (e.g., Summing numbers). 
    int sum = numbers.stream().reduce(0, (a, b) -> a + b);

8. Advanced Collectors (The Professional Level)

The Collectors utility class is where the complexity lies in backend engineering.

1. groupingBy (Categorization)

// Result: Map<Department, List<Employee>>
Map<String, List<Employee>> employeesByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

2. toMap (Mapping Objects)

// Map of ID to User Object
Map<Long, User> userMap = users.stream()
    .collect(Collectors.toMap(User::getId, user -> user));

3. Extreme Nesting (Multi-Level Grouping)

A Senior skill is grouping data by multiple criteria simultaneously.

// Goal: Map<Department, Map<Level, Double>> (Avg Salary per Level per Dept)
var complexReport = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDept,
        Collectors.groupingBy(
            Employee::getLevel,
            Collectors.averagingDouble(Employee::getSalary)
        )
    ));

4. teeing (Double Aggregation - Java 12)

Calculate two things at once! E.g., Average and Sum.

var summary = players.stream().collect(
    Collectors.teeing(
        Collectors.summingInt(Player::getScore),
        Collectors.averagingInt(Player::getScore),
        (sum, avg) -> new ScoreStats(sum, avg)
    )
);

9. Optional: The "Safety Box"

Optional<T> is a box. It might contain a value, or it might be empty. It prevents the NullPointerException "billion-dollar mistake".

The "Safe" Lifecycle

Optional<User> user = repo.findById(id);

// 1. Map if exists
Optional<String> email = user.map(User::getEmail);

// 2. Default value if empty
String out = email.orElse("default@mail.com");

// 3. Logic if exists
user.ifPresent(u -> System.out.println("Online: " + u.getName()));

// 4. Throw exception if empty
user.orElseThrow(() -> new RuntimeException("Not found"));

Senior Rule: No .get()!

Never call optional.get() without checking isPresent() first. Better yet, never use .get() at all. Always use orElse or ifPresent to maintain a clean functional flow.

10. Records: Immutability by Default (Java 14+)

Before Java 14, to create a simple Data Carrier class, you had to write 50 lines of boilerplate (Getters, toString, etc) or use Lombok.

Record Magic

public record UserDTO(Long id, String name, String email) {}

That's it. It's done. Java automatically generates Final fields, Constructor, Accessors (id(), name()), equals(), hashCode(), and toString().

  • Immutability: You cannot change a record's fields after creation. This makes them perfectly Thread-Safe.
  • Use Case: DTOs, API responses, Database rows.

12. Modern Switch Expressions

Switch is no longer a "clunky" statement from C. It is a powerful expression.

Old Switch vs New Switch

// OLD: Fallthrough bugs, break everywhere
int result;
switch(day) {
    case MONDAY: result = 1; break;
    default: result = 0;
}

// NEW: No breaks, returns value directly
int result = switch(day) {
    case MONDAY -> 1;
    case TUESDAY, WEDNESDAY -> 2;
    default -> 0;
};

13. Pattern Matching (The "Safety Cast")

Stop doing instanceof then (Casting). Do it all in one step.

if (obj instanceof String s) {
    // s is now a String variable, automatically cast!
    System.out.println(s.toLowerCase());
}

Combined with Switch (Java 21)

return switch (obj) {
    case String s -> s.length();
    case Integer i -> i;
    case List l -> l.size();
    default -> 0;
};

3. Parallel Streams: The Interview Trap

When NOT to use .parallelStream()

Beginners think it makes everything faster. Architects know it can kill performance. Avoid it if:

  • Your source is a LinkedList (hard to split).
  • You are doing I/O or Blocking calls (it blocks the common thread pool).
  • Your data set is small (< 10,000 items). The overhead of splitting is higher than the gain.

16. CompletableFuture: Async Mastering

Modern apps must not block. CompletableFuture represents a value that will arrive in the future.

CompletableFuture.supplyAsync(() -> userService.fetch(id))
    .thenApply(User::toDTO)
    .thenAccept(System.out::println)
    .exceptionally(ex -> {
        System.err.println("Failed!");
        return null;
    });

17. Virtual Threads: Project Loom (Java 21)

This is the most "Senior" topic in modern Java.

The Problem

For 25 years, 1 Java Thread = 1 Operating System Thread. OS threads use 1MB of memory and switching between them is slow. This limited Java to ~2,000 users per machine.

The Solution: Virtual Threads

Virtual Threads are "lightweight". They live on the Heap (like objects). You can start 1,000,000 virtual threads and the machine won't even sweat.

graph TD CarrierThread[Carrier OS Thread] VT1[Virtual Thread 1 - Request A] VT2[Virtual Thread 2 - Request B] VT3[Virtual Thread 3 - Request C] VT1 --> CarrierThread VT2 --> CarrierThread VT3 --> CarrierThread

Expert Tip: When NOT to use Virtual Threads

Virtual Threads are brilliant for I/O-Bound tasks (Database, API, File calls). However, they are **NOT** for CPU-Bound tasks (Video encoding, complex math, heavy encryption).

  • Reason: If a thread is crunching numbers, it never "yields" to wait for data. It stays stuck on the CPU. Creating 1 million CPU-hungry threads will just overload your processor and make the app slower than using 4 standard threads.

When Virtual Thread 1 waits for a Database, it "unmounts" from the OS thread, letting Virtual Thread 2 take over. Zero CPU time is wasted.

18. Performance & ZGC

Java 21 with the Z Garbage Collector (ZGC) can handle massive 1TB heaps with Zero "Stop-the-world" pauses. Previous versions of Java would freeze for 5-10 seconds to clean memory. ZGC does it in less than 1 millisecond.

How to enable ZGC

You don't need code changes, just a JVM flag when running your JAR:

java -XX:+UseZGC -XX:+ZGenerational -jar my-big-app.jar

19. Modern Java Interview Masterclass (Easy to Hard)

This section covers common questions asked in interviews for Junior, Mid, and Senior positions.

Level 1: Junior & Foundation

1. What is a Functional Interface? Give examples.

Answer: An interface with exactly one abstract method. It can have multiple default or static methods. Examples: Runnable (run), Comparator (compare), and the built-in Predicate, Function, Consumer.

2. What is the difference between a Collection and a Stream?

Answer:

  • Collection: An in-memory data structure that holds all its values. You can add/remove items.
  • Stream: A fixed-sequence view of data that doesn't store anything. It processes data on-the-fly.

3. What is the use of the Optional class?

Answer: It's a container used to represent a value that might be null. It forces you to handle the empty case explicitly, reducing the risk of NullPointerExceptions.

Level 2: Intermediate & Practical

4. Explain the difference between map() and flatMap().

Answer:

  • map: 1-to-1 mapping. (Transforming a User to their Email String).
  • flatMap: 1-to-Many mapping + Flattening. If you have List<List<String>>, flatMap converts it into a single Stream<String>.

5. How is orElse() different from orElseGet()?

Answer:

  • orElse(value): The value inside is created even if the Optional is NOT empty. (Can be wasteful).
  • orElseGet(Supplier): The supplier is only called if the Optional is empty. (More efficient for heavy objects).

6. What are "Effectively Final" variables in Lambdas?

Answer: A variable that is not declared final but whose value never changes after it is initialized. Lambdas can only access local variables that are effectively final to ensure thread-safety.

Level 3: Advanced & Architectural

7. Why shouldn't you use Optional for class fields or method parameters?

Answer: It is not Serializable. Storing it in fields can break session persistence. For parameters, it makes method overloading messy—it's better to just check for null or overload the method.

8. How do Virtual Threads improve performance over Platform Threads?

Answer: Platform threads are tied 1:1 to OS threads, which are heavy (1MB memory). Virtual threads live on the JVM heap and are multiplexed onto a few OS threads. When a Virtual Thread hits a blocking I/O (like DB call), it "yields" the OS thread so others can use it, maximizing CPU usage.

9. What is invokedynamic and how does it relate to Lambdas?

Answer: invokedynamic is a JVM instruction that allows the dynamic linking of code at runtime. Instead of creating a new class for every lambda (like anonymous classes do), Java uses invokedynamic to generate a call site that points to a private method containing the lambda logic, making it faster and memory-efficient.

10. What are the dangers of parallelStream()?

Answer: It uses a shared ForkJoinPool.commonPool(). If one parallel stream performs a slow/blocking operation, it can block all other parallel streams in the entire application. It also has overhead that makes it slower for small collections.
