Module 1 — Internet & Web Fundamentals

Goal: Understand exactly what happens between a user typing a URL and your Spring Boot controller method being invoked.

Why this module matters for backend engineers

  4. Load balancer health-check misconfiguration
  5. Connection pool exhaustion (backend side)

1.1 DNS Resolution

DNS = Domain Name System
Translates human-friendly names (api.myapp.com) into IP addresses (3.124.89.210 or 2600:1f18:abcd::1).

Modern DNS lookup steps (realistic order)

  1. Browser internal DNS cache
  2. Operating system DNS cache (systemd-resolved / Windows / macOS mDNS)
  3. Local recursive resolver (8.8.8.8, 1.1.1.1, ISP, dns.adguard.com, …)
  4. Root servers (13 logical clusters, hundreds of anycast instances)
  5. TLD servers (.com, .io, .dev, …)
  6. Authoritative nameservers (Cloudflare, Route 53, NS1, Vercel, …)
  7. Response + caching everywhere with TTL

Most important DNS record types (2025)

TypePurposeTypical TTLExample
AIPv4 address300–3600api → 3.124.89.210
AAAAIPv6 address300–3600api → 2600:1f18:abcd::1
CNAMEAlias (not at apex)60–300api-v2 → api.myapp.com
ALIAS / ANAMECNAME-like at apex zone60–300myapp.com → d1111.cloudfront.net
TXTSPF, DKIM, DMARC, verification3600+"v=spf1 include:_spf.google.com ~all"
TTL is the most dangerous DNS setting
High TTL (86400 = 24 h) → very slow propagation during fail-over, migration, blue-green switch.
Recommended ritual before DNS change: lower TTL to 60–300 s at least 24 h in advance.
Useful diagnostic commands (copy-paste friendly) 
# Quick lookup
nslookup api.myapp.com 8.8.8.8

# Full resolution path + timing
dig +trace api.myapp.com

# Show authoritative servers only
dig +short NS myapp.com

# Flush caches (common "it works now" fix)
# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Ubuntu / Debian
sudo systemd-resolve --flush-caches

# Windows (cmd as admin)
ipconfig /flushdns

1.3 HTTPS & TLS (2025 view)

TLS 1.3 handshake – simplified

  1. ClientHello (supported versions, ciphers, random, extensions: ALPN, SNI, key share)
  2. ServerHello + Certificate + Finished
  3. Client Finished
  4. Application data (encrypted)
TLS 1.3 advantages (why everyone moved)
  • 1-RTT handshake (faster than TLS 1.2)
  • Only 5 ciphers (much simpler & more secure)
  • Mandatory forward secrecy
  • Encrypted SNI possible (ECH – in progress 2025)

Common TLS termination patterns in 2025

LocationProsConsTypical users
Edge/CDN (Cloudflare, Fastly)Global anycast, WAF, cachingLess controlAlmost everyone
Load Balancer (ALB, NLB, GCP LB)Centralized cert managementCPU overhead on LBMost serious backends
Application (Spring Boot)End-to-end encryption, mTLSCPU cost, cert managementService mesh, zero-trust

2. Request Lifecycle in Spring Boot

Let’s follow a real GET /cases/123 request step-by-step.

Step-by-step journey

  1. Client sends request
    GET https://api.myapp.com/cases/123
    → usually goes through DNS → CDN → Load Balancer
  2. Load Balancer
    Distributes traffic across multiple application instances.
    Common choices: AWS ALB, Nginx, HAProxy, Traefik, Envoy
  3. Tomcat (embedded web server)
    Listens on port 8080 (default)
    Accepts TCP connection → parses HTTP → creates Servlet request
    Startup log example: 
    Tomcat started on port(s): 8080 (http) with context path ''
  4. DispatcherServlet (Spring MVC front controller)
    Central dispatcher — all requests go through it.
    Responsibilities:
    • Handler Mapping — finds matching @Controller method
    • Handler Adapter — invokes the method
    • View resolution / Response conversion (usually @ResponseBody → JSON)
  5. Controller layer
    Thin layer — should mostly:
    • Validate input
    • Call service
    • Return DTO / entity (auto-converted to JSON)
    @RestController
@RequestMapping("/cases")
class CaseController {

    private final CaseService caseService;

    @GetMapping("/{id}")
    public CaseResponse getCase(@PathVariable Long id) {
        return caseService.getCase(id);
    }
}
  6. Service layer
    Business logic, transactions, orchestration 
    @Service
@Transactional(readOnly = true)
class CaseService {

    public CaseResponse getCase(Long id) {
        Case c = caseRepository.findById(id)
            .orElseThrow(() -> new CaseNotFoundException(id));
        // business rules, permissions, mapping...
        return mapper.toResponse(c);
    }
}
  7. Repository layer (Spring Data JPA example)
    public interface CaseRepository extends JpaRepository {
    // custom queries if needed
}
    Generated SQL: SELECT * FROM cases WHERE id = ?
  8. Database
    Returns row → mapped to entity → returned back through layers
Typical latency breakdown (real production API ~120–250 ms)
  • Network / CDN / LB ~20–50 ms
  • Tomcat → DispatcherServlet ~3–8 ms
  • Controller + mapping ~2–10 ms
  • Service logic ~5–30 ms
  • Database query + network ~50–150 ms ← most common bottleneck

3. Threading Model in Spring Boot (Tomcat)

Default model: Thread-per-request (servlet 3.1 blocking I/O)
1 incoming request → 1 dedicated thread from Tomcat thread pool

Thread pool configuration (common defaults & tuning)

server.tomcat.threads.max=200              # max concurrent requests
server.tomcat.threads.min-spare=10           # minimum idle threads
server.tomcat.accept-count=100               # queue size when all threads busy
server.tomcat.connection-timeout=20000       # 20s
If 200 threads are busy and 150 more requests arrive → 150 go into queue.
Long queue → high latency → timeouts → bad user experience.

Blocking vs non-blocking in practice

Operation typeThread behaviorConcurrency impactExample
Blocking (default)Thread waitsLimited by thread pool sizeJPA .findById(), JdbcTemplate.query()
Async controllerThread released earlyHigher throughput possibleCompletableFuture, @Async, WebClient
Reactive (WebFlux)Event-loop (few threads)Very high concurrencyMono/Flux, R2DBC, WebClient
Async controller example (simple but powerful) 
@GetMapping("/slow/{id}")
public CompletableFuture<CaseResponse> getCaseAsync(@PathVariable Long id) {
    return CompletableFuture.supplyAsync(() -> 
        caseService.getCase(id), taskExecutor);
}

→ Tomcat thread is released while supplyAsync runs on separate thread pool

4. JVM Memory Model (HotSpot 2025 perspective)

JVM Process Memory
├── Heap                 ← objects live here
│   ├── Young Generation (Eden + Survivor)
│   └── Old Generation
├── Metaspace            ← class metadata
├── Thread stacks        ← one per thread (~1 MB each)
├── Direct memory        ← off-heap (Netty, ByteBuffers...)

Heap tuning flags (very common in production)

-Xms4g               # initial heap size
-Xmx4g               # max heap size
-XX:+UseG1GC         # most common GC 2024–2026
-XX:MaxGCPauseMillis=200
-XX:+AlwaysPreTouch
-XX:+UseStringDeduplication

Common GC behavior patterns

  • Minor GC — fast, frequent (young gen), usually < 50 ms
  • Mixed GC (G1) — cleans young + some old regions
  • Full GC — slow (seconds), stop-the-world, should be rare
Very common production problems caused by heap pressure
  • Large JSON responses / reports → huge temporary objects
  • Unbounded caches → Old Gen fills up → frequent Full GC
  • Memory leak in ThreadLocal / caches → slow death

Monitoring must-have metrics

  • Heap used / committed / max
  • GC pause time & frequency (young / mixed / full)
  • Allocation rate (MB/s)
  • Old Gen occupancy before/after GC
  • Thread count (live / daemon)

Key Takeaways & Production Mindset

After this module you should understand:
  • Full request path: Client → LB → Tomcat → DispatcherServlet → Controller → Service → Repo → DB
  • Thread-per-request model → thread pool saturation is a major bottleneck
  • Blocking I/O wastes threads → async or reactive helps under high concurrency
  • Heap pressure (allocation rate + GC behavior) is one of the top 3 causes of latency spikes
  • Most real latency usually comes from: database / external calls / GC pauses
